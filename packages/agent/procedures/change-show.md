# Change an existing paid booking

Get current authenticated context using [[tool:get_session_context]], then actually call [[tool:list_my_bookings]] for a member or [[tool:find_booking]] with required verification for a guest before replying. Saying you need to look is not the lookup. "Make changes to my current booking" refers to confirmed bookings even when activeOrder is empty; do not ask for a reference first. Match known film/date/experience, asking which only if several still match. Retain its film, cinema, experience, ticket composition, original time, seats, paid amount, offers and food.

Identify the requested change separately from the existing booking. For a reference-less request with only one owned booking, briefly identify it and confirm it is the intended booking; "yes, that one" confirms identity only. "The one today at Deira" likewise answers which booking, not a same-day replacement. If no new date/time/experience or other change has been requested, ask what the guest wants to change and wait BEFORE [[tool:prepare_swap]] or any replacement search. Do not copy the original booking's date into a desired target. If the booking and change were already explicit, carry them forward without redundant confirmation. A needs swap_change result means the desired change is still missing, not permission to pick one.

Search the requested day first at the SAME cinema for the SAME film. Prefer the original experience and closest suitable time, price and available seats; use verified seating preferences when exact seats cannot be kept. Start with [[tool:prepare_swap]] using the verified bookingId and requested date/time, omitting targetSessionKey when none was selected. Its needs swap_session response supplies the closest same-cinema alternatives; choose the strongest matching returned candidate for a read-only priced preview, then ask for consent. Use [[tool:search_sessions]] only when an additional explicit filter is needed, keeping the verified cinema and film; [[tool:get_seat_plan]] supplies actual map availability when requested. “Tomorrow instead” changes the date, not the cinema or film. Never silently broaden to another cinema. If none fits, explain that specific limitation and ask whether to change time, experience or cinema before expanding that constraint.

If prepare_swap returns recommendedPreviewInput, call [[tool:prepare_swap]] again with that exact input before replying. This obtains a seat-and-price preview; it neither changes the booking nor takes payment. A request for tomorrow at the same/closest time already authorizes this read-only selection: do not ask the guest to choose from the returned times again. If the scoped result is empty, explain the missing match and ask which date/time, experience or cinema constraint the guest wants to change. Wait for that answer BEFORE any wider lookup, including dropping the time filter at the same cinema. A failed lookup means availability could not be checked; it supplies no permission to widen the search or add a film-language argument.

Use [[tool:prepare_swap]] for a proposed target; it is a preview, not a completed exchange. Show the original and proposed show/experience/seats together and state only the returned price difference, extra amount due or refund handling. Describe changed food/offer conditions if the result supplies them. Do not reconstruct arithmetic from old and new sticker prices, claim a full replacement charge is merely the difference, or promise a food transfer not supported by the result.

If it returns needs swap_refund_method, the cheaper replacement still needs a refund destination. State the returned difference and permitted methods/timelines, then ask which method the guest prefers. Do not treat an omitted method as original-card consent or ask to confirm the exchange yet; this result has no confirmationId. After the guest chooses, call [[tool:prepare_swap]] for the exact returned targetSessionKey and bookingId with that refundMethodForDifference, preserving the selected show/seats. Use the resulting preview for a separate exchange confirmation. A previous explicit permitted method need not be asked again; a rejected/unavailable choice needs a new supported choice. A successful widget swap.refund.choose event means only that the destination was selected and the final preview prepared: use its returned confirmationId and wait for the separate exchange decision, without repeating preparation or claiming an exchange/refund completed.

If the backend reports unsupported settlement, an ineligible booking, lost offer, mismatched seats or an uncertain payment, explain the returned limitation and stop before mutation. Offer supported alternatives or Customer Care; never silently cancel and buy a replacement as a workaround.

Wait for explicit consent to the specific target, changed seats/experience and actual extra/refund amount. Only then call [[tool:swap_booking]] with its current confirmationId and confirmed true. The backend's settlement path determines whether a secure payment step is required; opening a sheet is not payment. Never invent a token or issue a fresh full-price payment pretending it is a difference charge.

For queued/running actions use [[tool:get_action_result]] with the returned actionId. Until terminal success, the original booking is not known to be replaced. After success, give one brief result and point to the updated receipt/reference/QR; do not recap every unchanged detail or promise email delivery.
