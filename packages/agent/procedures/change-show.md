# Change an existing paid booking

Get current authenticated context using [[tool:get_session_context]], then identify the booking with [[tool:list_my_bookings]] or [[tool:find_booking]] and required verification. Clarify only if multiple bookings could match. Retain its film, cinema, experience, ticket composition, original time, actual seats, paid amount, offers and food.

Search the requested day first at the SAME cinema for the SAME film. Prefer the original experience and closest suitable time, price and available seats; use verified seating preferences when exact seats cannot be kept. Start with [[tool:prepare_swap]] using the verified bookingId and requested date/time, omitting targetSessionKey when none was selected. Its needs swap_session response supplies the closest same-cinema alternatives; choose the strongest matching returned candidate for a read-only priced preview, then ask for consent. Use [[tool:search_sessions]] only when an additional explicit filter is needed, keeping the verified cinema and film; [[tool:get_seat_plan]] supplies actual map availability when requested. “Tomorrow instead” changes the date, not the cinema or film. Never silently broaden to another cinema. If none fits, explain that specific limitation and ask whether to change time, experience or cinema before expanding that constraint.

Use [[tool:prepare_swap]] for a proposed target; it is a preview, not a completed exchange. Show the original and proposed show/experience/seats together and state only the returned price difference, extra amount due or refund handling. Describe changed food/offer conditions if the result supplies them. Do not reconstruct arithmetic from old and new sticker prices, claim a full replacement charge is merely the difference, or promise a food transfer not supported by the result.

If the backend reports unsupported settlement, an ineligible booking, lost offer, mismatched seats or an uncertain payment, explain the returned limitation and stop before mutation. Offer supported alternatives or Customer Care; never silently cancel and buy a replacement as a workaround.

Wait for explicit consent to the specific target, changed seats/experience and actual extra/refund amount. Only then call [[tool:swap_booking]] with its current confirmationId and confirmed true. The backend's settlement path determines whether a secure payment step is required; opening a sheet is not payment. Never invent a token or issue a fresh full-price payment pretending it is a difference charge.

For queued/running actions use [[tool:get_action_result]] with the returned actionId. Until terminal success, the original booking is not known to be replaced. After success, give one brief result and point to the updated receipt/reference/QR; do not recap every unchanged detail or promise email delivery.
