# VOX procedure release

Four free-form Procedures keep one public agent and its current voice. Their concrete triggers separate new/unpaid bookings, cancellation, date changes and missing-payment investigation. A fifth structured Procedure acknowledges an explicit brevity-only request in English or Arabic, without inventing a booking selection or appending a question. General information, language, privacy, silence and tool-result truth remain shared rules. `demo-policy.md` is a source note, not a Procedure.

Native tests demonstrated a narrow use for a structured reply: an Arabic brevity-only request produced an unsupported selection and ticket quantity despite the shared instructions. `brief-acknowledgement.json` contains only a language branch and an exact Say step; it performs no business action. The API calls this type `deterministic`. The consequential flows still require backend eligibility, order-version checks, pending-action resolution and explicit consent. Do not add automatic financial retries.

## Local preparation

- `agent:export` produces reviewable sources and 42 synthetic scenario segments, including child-age restrictions, accepted proposals, failed actions and fresh reviews after offer removal. Its `agent.json` is a new-agent example, not a safe update for an existing agent.
- Author tool references as `[[tool:name]]`. `buildProcedures` validates each name against the current contracts and resolves it to `[tool id="..."]` from the complete candidate map. Changed tool schemas receive new IDs; rebuild every Procedure reference when that map changes.
- `materialize-simulations.ts tool-map.json output.json journeys` resolves every attached tool to a mock. All tools, including future/unexpected actions, use `mocking_strategy: all` and `fallback_strategy: raise_error`. Payment execution is always an error fixture. No real booking/payment is executed by these simulations.
- The eight journeys are tested in English and Arabic with success/refusal boundaries. They are bounded conversation segments, not proof of browser layout, file download, actual payment rails or human listening. Review traces with `audit-simulation-evidence.ts` in addition to the provider judge; provider passes alone are not acceptance.
- The synthetic clock is 3 June 2030 at 16:40 Dubai. Apply it only as an ad hoc simulation override; never save it to the agent. Mock responses are stateless, so proposal acceptance and fresh checkout after offer removal have separate segments with the appropriate initial state; browser/backend tests verify the full state transition.

## Candidate lifecycle

1. Read the latest main configuration and branch version. Create an isolated branch on the same agent; keep the user's current primary and Arabic voices, model, backups, security, privacy, timing, greetings and dynamic clock. Do not clone a new public agent or move regions.
2. Wait for the corresponding backend contracts to be deployed before unmocked candidate calls. Create immutable revisions only for changed tool definitions; leave shared old tools intact. For the six reviewed knowledge documents, create candidate replacements and preserve the other attached documents; do not overwrite shared main documents. Verify RAG readiness and the selected document IDs/content.
3. Candidate synchronization requires explicit `--apply`, `ELEVENLABS_AGENT_ID`, `ELEVENLABS_BRANCH_ID`, `ELEVENLABS_MAIN_BRANCH_ID`, `ELEVENLABS_EXPECTED_VERSION`, `ELEVENLABS_DEPLOYMENT_REPORT` and the existing secure API/tool credentials. Only the configured EU API is allowed. The script cannot publish main.
4. The lifecycle creates/updates the five procedure drafts using their authored types, compiles them into the provider workflow, rechecks the expected branch head, then publishes prompt/tools/workflow to that candidate. It refuses unknown procedures/workflows or different unpublished drafts. No automatic draft deletion, branch merge or main deployment occurs.
5. Read back the published version and every procedure's referenced tool IDs. Verify voice/model/privacy/timing settings are unchanged. A failed post-publication check blocks promotion; retain the candidate and evidence for inspection. A compile failure leaves unpublished drafts, not a successful release.
6. Run the new mocked journeys, existing relevant regressions and the independent audit against that exact candidate version. Exercise consent refusals, wrong booking/persona, missing quantity, child eligibility, bank/credit conflict, payment uncertainty, same-cinema constraints and unsupported settlement. For actual voice tests verify the real conversation's branch/version and language-specific voice; textual simulation is not audio acceptance.
7. Main promotion is a separate root-owned, authorized step after the matching app release and acceptance. Read the newest main again and inspect the merge preview so a later user voice/config edit is preserved. Read back the final main version, procedure/tool/KB references and protected settings; smoke-test without real financial activity. Keep the previous version available for rollback.
