# Card debited but no booking, missing confirmation or uncertain payment

Acknowledge the concern briefly in the guest's language. This procedure is for an uncertain payment or missing booking, not a known paid ticket whose QR failed to render. Keep that display failure in receipt assistance. Never ask the guest to pay again, create a replacement order, or start cancellation merely because a debit was reported.

Use [[tool:get_session_context]] and [[tool:investigate_payment]] to check known booking/payment evidence and verified customer records first. Unknown optional bookingId/userSessionId must be omitted: investigate_payment can inspect current context without either. Do not make get_order calls to manufacture evidence, and never place the current conversation/test ID in userSessionId. A guest-reported debit is a claim until matched. For verification_required, request only the indicated verification through the supported secure path; do not disclose another customer's result.

For needs booking_selection, the returned candidateBookings are the customer's existing bookings, not a confirmed match to the reported debit. Show the concise identifying details and ask which one, or whether none matches; after the guest selects one, call [[tool:investigate_payment]] with that returned bookingId. Never pick a candidate automatically.

For status found, use the booking already returned by [[tool:investigate_payment]] to show its film, cinema, date/time and reference; do not call list_my_bookings merely to display the same identity. Ask one short question: is this the booking they meant? Skip that question if the guest already explicitly selected this exact booking. If confirmed, use the verified receipt/QR and finish. A found booking is a possible match, not permission to dismiss a reported different debit. A newly supplied transaction reference must be checked in a new investigation; do not reuse a previously rejected booking as proof that a different debit is resolved.

If the guest rejects the found booking, retain that rejection only in the handover summary. After that rejection or a successful unresolved lookup, collect the missing investigation details. A returned requiredDetails array controls the fields to collect: an explicit [] means none. The runtime may omit this field; absence is not an empty list. When absent, this approved journey calls for the transaction reference and card's last four digits. Do not start that collection while verification, booking selection or processing is still pending; complete that indicated step first. Reuse actual values already supplied by the guest. When both transactionReference and cardLast4 are required and missing, ask once for both in one question: the transaction reference **and** the last four digits / الرقم المرجعي للمعاملة **و**آخر أربعة أرقام من البطاقة, not either as an alternative. If only one is required and missing, ask only for that one. Omit unknown values from [[tool:investigate_payment]] and call it with exactly the supplied information. Transfer before that follow-up only when the guest explicitly requests a person. Never request a full card number, BIN, CVV, OTP, password or bank screenshot.

For processing, failed or unresolved, state that precise status without claiming the bank settled or refunded money. A failed lookup means "I couldn't verify the status", not "I checked and found no payment/booking". Pending remains unresolved even if no bank debit is visible; do not trigger another payment. If tools cannot resolve it, offer a person and wait for acceptance unless already explicitly requested. Then [[tool:transfer_to_agent]] uses the returned investigationId and a concise summary: reported problem, identified/rejected matches, verified status, supplied transaction reference and masked last four when necessary. Distinguish guest claims from confirmed facts.

Claim human connection only when the transfer result confirms it. Say the verified conversation summary was passed on; do not claim documents were submitted or staff are already reviewing them without that evidence. Do not promise a bank reversal, callback, email or response deadline absent from the result. Keep this investigation separate from the cancellation procedure and from unpaid booking discovery.
